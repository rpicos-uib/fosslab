FOSSLab runs every program inside one container image (IIC-OSIC-TOOLS, with the IHP SG13G2 PDK) through Apptainer, as the user who starts it. Students log into one server; each has a workspace in their home; teachers read every workspace from one window.

Install on the server (Scientific Linux 7, also EL8/9/10)

  1. Copy the fosslab folder to the server and edit install/fosslab.conf: teachers' user names, groups, image version, tutorial URL.
  2. Run, as root: 
    $ sudo ./install/install.sh
    It goes through six steps (each can be run again on its own, e.g. install.sh 40 50):
    StepDoes
    10host packages: points SL7's and EPEL 7's repositories to their archives (both are end-of-life), installs Apptainer, ACL tools, X11 forwarding, fonts, and X2Go with XFCE
    20lets normal users run Apptainer (setuid helper, or user namespaces)
    30the image: builds iic-osic-tools_<tag>.sif from Docker Hub (about an hour, ~45 GB free during the build, ~15 GB after), or downloads one built elsewhere with install/build_sif.sh
    40FOSSLab into {{prefix}}, /etc/fosslab.conf, the PATH, desktop menu entries
    50groups fosslab (students) and fosslab-staff (teachers)
    60the self-test as a teacher: every tool and the full IHP flow
  3. Add the students, from a CSV file (user,Full Name[,password]) or by name: 
    $ sudo ./install/add_students.sh students.csv
    New accounts without a password get a random one (in /root/fosslab_passwords.txt), to be changed at the first login.

Courses

Each course has its own teachers, its own students and its own settings, so several courses (or several editions of one) can run on the same server. A student can be in several courses: they work in a separate folder for each, ~/fosslab-<course>, and switch with File > Course. Only a course's own teachers see its students' work.

Everything is in the Supervisor's Courses menu:

Menu entryWhat it does
New course (wizard)...Five pages: Course (id, e.g. micro-2026, and title), Teachers, Students (add them one by one, Import CSV... or Paste a list... copied from a spreadsheet: user name and full name per line), Teaching (teachers may read, or read and write, the students' work; the tutorial's op-amp as a library: none, one shared read-only copy, or a copy of their own; the tutorial's address) and Review (what applying it will change).
Edit course..., Students...The same pages, for an existing course. Students also shows the first password of every account the course created.
Apply changes...What will change on the server, and the command that does it (below).
Duplicate as...A new course from an existing one, with or without its students: next year's edition in a minute.
Load from file..., Save to file...Keep, share or reuse a course as a file.
Archive...Hide a finished course from its students' list. Nothing is deleted.
Edit system configuration...Edit a copy of /etc/fosslab.conf (install location, image, folders the tools see...), with the command that installs it.

Applying. FOSSLab runs without root, so it never changes the server by itself: a course is saved as a draft (~/.config/fosslab/courses/<id>.course) and a teacher of the course with sudo rights applies it, in a terminal on the server:

$ sudo {{prefix}}/bin/fosslab-course apply ~/.config/fosslab/courses/micro-2026.course

It creates the groups fl-micro-2026 (students) and fl-micro-2026-t (teachers); creates a local account, with a random first password to be changed at the first login, for every student that has none (existing accounts, local or from the university's directory, are only added); creates each student's workspace and gives the course's teachers access to it, and to nothing else; sets up the example library; and stops the access to removed students' work, keeping their accounts and files. It can be run again at any time. Check in the Apply dialog confirms it was done; restart the Supervisor to see the new students. On the server, fosslab-course list shows your courses and fosslab-course show ID one of them.

A course is a plain text file (id, title, teacher, access, example, student user Full Name... one per line), so it can also be written by hand or generated from another system. The applied ones are in {{prefix}}/courses, readable only by each course's teachers. To move to a new server: install FOSSLab, copy {{prefix}}/courses and {{prefix}}/shared, and apply each course again.

From the single-course setup. Installing this version turns the existing students (group fosslab) into the course default, whose students keep ~/fosslab, and whose teachers are those of FOSSLAB_TEACHERS.

Supervising

Start fosslab-supervisor (desktop menu: FOSSLab Supervisor). It is the Library Manager plus a Course and a Student selector and a Roster:

  • The roster lists every student of the course with their libraries, cells, last change and how many simulations, DRC, LVS and PEX runs pass; private notes per student; export to CSV.
  • Choosing a student shows their workspace for that course, read only: open any view, browse the hierarchy, look at their DRC/LVS reports. Flows you run on their cells write to your own workspace (~/fosslab/.fosslab/supervisor/<course>/<student>), never to theirs.
  • Copy to my workspace on any of their cells, to try a fix.

Access works through file ACLs, not passwords: each course's teachers' group can pass through the students' homes and read (or, if the course says so, also write) their course workspace, and new files inherit that. Nothing else in the students' homes is visible.

The reference op-amp library

Everything in chapters 2 to 11 (numbers and screenshots) comes from a reference library that FOSSLab generates, so you can reproduce it, give it to the students, or change it:

$ fosslab example opamp                # library opamp_tut in your workspace
$ fosslab example opamp --solution     # also the exercise's solution (opamp_2pole.va, setup model_2pole)

It writes the op-amp (schematic, symbol, layout), the testbenches tb_opamp_ac and tb_opamp_tran with their Simulation Environment setups (outputs and specifications, 15 corners, Monte Carlo), the op-amp's Verilog-A view opamp.va, and the setup model of tb_opamp_ac that simulates it instead of the transistors. The model is compiled when a simulation first needs it (or by hand: fosslab va opamp_tut opamp).

Giving it to the students is a course setting (Teaching page: a shared read-only copy, or a copy of their own). By hand, without courses: generate it without the solution in a workspace of your own (e.g. a course account, or your ~/fosslab) and make that workspace readable by the students' group. Each student adds one line to their ~/fosslab/fosslab.lib (File > Edit library definitions):

INCLUDE /home/teacher/fosslab/fosslab.lib

The reference library then appears in their Library Manager, read only; Copy cell... gives them an editable copy of any cell.

Changing the example

The generator is {{prefix}}/app/fosslab/examples/opamp.py: the device sizes (MOS, CC_SIDE), the testbenches' control blocks (AC_CONTROL, TRAN_CONTROL), the setups with specifications and corners (ac_setup(), tran_setup(), va_setup()) and the model's parameters. The layout is drawn by examples/opamp_layout.py with IHP's PCells and reads the sizes from opamp.py; its placement and routing rules are explained at the top of the file. After a change, generate into a new library (--lib opamp_v2) and check it: fosslab drc|lvs opamp_v2 opamp.

All the tutorial's screenshots and numbers come from the real programs, and can be retaken on your own server: in the Library Manager, Tools > Retake tutorial screenshots... (or fosslab shots). It rebuilds the op-amp from scratch in a folder of its own (~/fosslab-shots, never your workspace), runs every flow, takes every screenshot and shows every number the chapters quote next to the value on your machine, in red where they differ. It takes about 10 minutes, on a private display unless you tick On my display (then the pictures show your desktop). From a git clone, bash tests/server_shots.sh does the same and also copies the pictures into the plugin and rebuilds its zip.

The exercise: answer key

QuestionExpected answer
1. GBW = 16.17 MHz, FP2 = 30 MHzUGF ≈ 14.6 MHz, PM ≈ 63.7° (by hand: UGF·√(1 + (UGF/30 MHz)²) = 16.17 MHz gives 14.55 MHz, and 90° − arctan(14.55/30) = 64.1°). The second pole reduces |A| near the UGF, so the gain reaches 1 earlier: with two poles UGF < GBW. (With all _sd at 0: otherwise Run nominal draws one random op-amp.)
2. CalibrationFP2 = UGF / tan(90° − PM) = 16.17 / tan(29.62°) ≈ 28.4 MHz; GBW = 16.17 · √(1 + (16.17/28.4)²) ≈ 18.6 MHz (GBW_sd scaled to ≈ 0.262 MHz). Model: 16.2 MHz, 59.8° (the small error: the dominant pole's own phase and the rounding).
3. Monte CarloUGF 16.16 ± 0.18 MHz, PM 59.9 ± 0.29°, offset 1.58 ± 2.04 mV.
4. Spread of PMFrom the GBW spread: UGF moves with GBW while FP2 is fixed, so UGF/FP2 and the PM change. It matches the transistors' σ (0.30°) here by coincidence of the two mechanisms; a model with correlated GBW and FP2 (both set by the bias current) would be more faithful.
5. Second polep2 ≈ gm6 / (2π (CL + C1)) with the Miller effect, and a right-half-plane zero at gm6/(2π Cc) that also costs phase: the calibrated FP2 lumps both.

The solution is the view opamp_2pole.va of cell opamp and the setup model_2pole of tb_opamp_ac, written with --solution; keep it out of the students' reach (generate it in a library they cannot include).
